# 项目面试问答速记

## 一、项目概览类

**Q1. 用一分钟介绍这个项目**
基于 FinDKG 时序金融知识图谱(WSJ 新闻抽取,1.3万实体、24万条带周粒度时间戳的四元组)构建投资研究系统。核心是 Orchestrator–Critic 双智能体架构:Orchestrator 通过 Anthropic Tool Use 自主编排 4 个工具(KG 信号、FRED 宏观、历史评分、结构化报告输出)做多轮推理;独立 Critic 审查草稿的信号冲突和过度自信,不通过触发修订。配套反馈闭环(用户评分按信号类型聚合回灌)和信号一致性回测。

**Q2. 为什么用知识图谱而不是直接把新闻全文给 LLM?**
三点:结构化事件已经完成信息压缩,同样上下文预算能覆盖 12 周事件而不是几篇文章;关系类型带极性(Invests_In/Negative_Impact_On)可以程序化聚合成可量化信号,新闻全文做不到;时间戳支持回测验证,能客观检验信号质量。

**Q3. 项目最有挑战/最得意的部分?**
手写 agentic loop 而非套框架:自己管理消息历史、解析 tool_use 块、设计 emit_report 强制结构化输出、MAX_ITERATIONS 防死循环。难点在让"模型自主决策"和"流程可控可测"共存——最终用 stub client 做到零 API 成本测试整个循环。

## 二、架构与 Agent 设计类

**Q4. Orchestrator 的 agentic loop 具体怎么运作?**
维护 messages 列表,每轮调 `messages.create` 带上 4 个工具 schema;模型返回 tool_use 块就执行对应工具,结果以 tool_result 追加回历史,进入下一轮;直到模型调用 emit_report(输入即结构化草稿,借 JSON schema 强制字段完整)或达到 10 轮上限。工具调用全程记录 trajectory,附在最终报告里保证可审计。

**Q5. Critic 是怎么设计的?为什么要独立?**
独立类、独立模型配置、一次独立调用。审查三点:KG 与宏观信号方向是否冲突且报告是否处理、置信度与数据量是否匹配、结论是否有数据支撑。输出严格 JSON(approved/conflicts/建议)。独立的意义:生成者自查有确认偏误,换一个"角色"和干净上下文审查效果更好,也便于给 Critic 换更便宜或更严格的模型。

**Q6. Critic 审查不通过后修订是谁做的?**
Orchestrator(金融研究员人格),不是 Critic——Critic 只挑错不动笔。修订用 `tool_choice` 强制调用 emit_report,保证修订稿仍严格符合 schema,避免自由文本 JSON 解析失败。

**Q7. 为什么不用 LangChain/AutoGen 这类框架?**
流程是单一固定流水线(loop→critic→revise→render),框架解决的多模型适配、链路组合问题在这规模下用不上。手写让每环透明:工具日志、终止条件、修订触发都是自己代码,测试可以 stub client 直驱。MCP 承担了工具协议标准化,算是更厂商中立的"半个框架"。

**Q8. MCP Server 在项目里起什么作用?**
把 KG 查询和宏观工具用 FastMCP 封装成 stdio server,可注册进 Claude Desktop 独立使用。关键设计:MCP server 和 agentic loop 共用 tools/ 层同一份实现,避免双份逻辑漂移。

**Q9. 单 Agent 和 Multi-Agent 模式差别?**
单 Agent 一次调用:KG 摘要拼 prompt 直接生成建议,快且便宜,是基线。Multi-Agent 增加:自主决定查什么(可能查宏观、查历史评分)、Critic 审查、修订,更慢更贵但有质量把关。保留单 Agent 作对照组。

## 三、知识图谱与数据类

**Q10. FinDKG 的结构?**
四元组(主语,关系,宾语,周):13645 实体分 12 类(人物、公司、国家、经济概念、指标等,不只是公司),15 种关系,261 周(2018-01~2023-01)。本质是"每周新闻事件的结构化快照",动态图而非静态图。

**Q11. 正负面信号怎么定义的?谁定的?**
项目自定义(数据集不自带极性):Positive_Impact_On/Raise/Invests_In 为正,Negative_Impact_On/Decrease 为负,其余 10 种中性。依据是关系语义的方向性。局限:忽略了中性关系里的隐含信息(如 Control、Operate_In 的语境),且未区分主语/宾语方向的受益差异——这是可改进点。

**Q12. 为什么不用 Neo4j?**
查询模式只有"按实体+时间窗过滤",无多跳遍历需求;4MB 数据 pandas 内存表毫秒级响应。图数据库在多跳推理、超内存规模、多服务共享时才有收益,当前引入只增加部署复杂度。

## 四、验证与质量类

**Q13. 怎么验证系统输出有价值?(必问)**
信号层:一致性回测——站在历史时间点 T 只用 T 前 12 周数据判方向,再看 T 后 8 周事件是否同向,得分[-1,1],滚动 10 窗口算平均分和胜率。严格避免 look-ahead bias。坦承:这不是收益回测,验证的是信号自洽性,新闻信号到股价还隔着市场定价。报告层:反馈闭环,用户评分按关系类型聚合(Invests_In 均分 0.786 vs Decrease 0.667),并作为工具回灌给 Agent。

**Q14. 项目已知的最大问题?(主动讲,加分)**
时间错位:KG 截止 2023-01,宏观是实时数据,报告会把 2022 年底事件和当前宏观当同一截面分析;且 Critic 的上下文摘要丢了日期字段,查不出来。修复方向:prompt 标注数据时段+Critic 审查清单加时效性检查。另一个:Critic JSON 解析失败时默认放行,兜底偏宽松,应改为标记不可信。

**Q15. LLM 幻觉怎么控制?**
四道措施:工具返回真实数据作为推理依据(grounding);emit_report 用 JSON schema 约束输出结构;Critic 专查"结论是否有数据支撑";报告附完整工具调用轨迹可回溯核对。坦承残余风险:模型复述数字仍可能出错(如自己数信号条数),Critic 目前只看压缩摘要查不全。

## 五、工程类

**Q16. 测试怎么做的?LLM 应用怎么测?**
52 个 pytest 单测,关键手法:合成最小 KG 数据集测查询层;stub LLM client(按脚本回放响应)测 agentic loop 的三种终止路径和 Critic 的 JSON 容错分支——零 API 成本、确定性、可进 CI。已知行为(如 Critic 失败默认放行)用测试显式钉住,改动会先触发测试失败。

**Q17. 做过什么重构?为什么?**
三轮:抽 tools/ 共享层消除 agentic loop 与 MCP server 的双份实现;统一配置(原 config 定义了但无人引用,模型名各处硬编码不一致);把 760 行单体 Orchestrator 拆成 loop/critic/renderer/store 四个单一职责模块(renderer 是纯函数,最易测)。另移除了效果不完善的嵌入相似度预测模块——做减法也是设计决策。

**Q18. 成本/延迟考虑?**
分级用模型:各 Agent 独立配置,主链路 Haiku,Critic 可独立换更便宜模型;max_tokens 按环节设预算(Critic 1024、宏观 512);事件截断(每类 6 条)控制上下文;MAX_ITERATIONS=10 兜底防失控调用。
