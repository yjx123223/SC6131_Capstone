# 知识图谱消融实验设计

> 目的：用可复现的实验回答"**在这个系统里，结构化知识图谱 + 规则推理，相比让 LLM 自己用 tool use 做多跳分析，到底有没有优势**"。
> 状态：设计稿，尚未实现。实现代码将放在 `eval/`。

---

## 1. 研究问题与假设

**RQ1**：引入产业链视角（不论用什么方式）能否提高报告对跨公司风险的覆盖？
**RQ2**：把多跳推理交给结构化图谱 + 确定性规则，相比交给 LLM 自由发挥，在覆盖率、可核验性、稳定性、成本上各有什么差异？

| 编号 | 假设 | 主要验证指标 |
|---|---|---|
| H1 | 有产业链信息的报告，跨公司风险覆盖显著高于无产业链信息 | M1（A vs B、A vs C） |
| H2 | 图谱版在 **2 跳**（上游供应商）风险上的覆盖高于纯 tool use | M2（B vs C） |
| H3 | 图谱版的引用更可核验、编造更少（事件有编号和来源） | M3、M4 |
| H4 | 图谱版多次运行的结果更稳定（推理部分是确定性的） | M6 |
| H5 | 图谱版成本更高（事件抽取是额外的 LLM 调用） | M5 |

H5 预期为"劣势"。**如实报告取舍**，不追求全面获胜。

## 2. 实验组

| 组 | 可用工具 | system prompt | 说明 |
|---|---|---|---|
| **A 基线** | `query_market_data`、`query_news`、`query_sec_filings`、`query_macro`（仅限目标公司） | 现有 prompt 去掉图谱相关段落 | 只看目标公司自身 |
| **B 纯 tool use** | 同 A，但**允许对任意公司调用** `query_news` / `query_market_data` | A 的 prompt + 附上种子关系文本（"AAPL 的供应商有 TSM、AVGO、QCOM；竞争对手有 GOOGL、MSFT……"）+ 一句"你可以查询相关公司的新闻，自行判断风险传导" | LLM 自己决定查谁、怎么推理 |
| **C 图谱版** | A 的工具 + `query_company_graph` | 现有 prompt | 当前实现 |

**关键点**：B 组拿到的**关系信息与 C 组完全相同**（同一份 `seed_relations.csv`），差异只在于"关系以文本给模型自由使用" vs "图谱结构化 + 规则推理"。这样 B↔C 的差距才能归因到设计本身。

A、B 组不产出 `supply_chain_analysis` / `cited_event_ids` 字段；报告模板对应减少两节。

## 3. 样本

从种子文件中选取 **15 家公司**，覆盖不同的邻居规模，其中 12 家有 2 跳上游：

| 公司 | 1 跳 | 2 跳 | 公司 | 1 跳 | 2 跳 |
|---|---|---|---|---|---|
| AAPL | 5 | 1 | NVDA | 5 | 1 |
| MSFT | 5 | 1 | AMD | 4 | 1 |
| GOOGL | 5 | 1 | ORCL | 3 | 1 |
| AMZN | 5 | 1 | TSLA | 3 | 1 |
| META | 2 | 1 | NFLX | 2 | 1 |
| AVGO | 2 | 1 | QCOM | 2 | 1 |
| TSM | 5 | 0 | INTC | 3 | 0 |
| ASML | 2 | 0 | | | |

每家公司 × 3 组 × **重复 3 次** = **135 份报告**。

## 4. 控制变量

| 变量 | 处理方式 |
|---|---|
| **外部数据** | 实验前一次性**录制快照**：对每家公司及其全部邻居，录下 4 类工具的返回结果，存成 JSON。三组全部从快照回放，保证看到的数据完全一致，也避免重复请求外部接口 |
| **随机性** | 所有 LLM 调用 `temperature=0`；同一配置重复 3 次以观察残余波动 |
| **模型** | 报告生成与评审统一用 `claude-haiku-4-5`（见下方"评审模型的选择与风险"） |
| **执行顺序** | 三组交错执行，避免接口状态漂移影响（回放快照后此项影响已很小） |
| **失败处理** | 单次运行报错时最多重试 1 次，仍失败则记为 failed 并在结果中标注，不静默丢弃 |

快照口径：录制当天的数据；报告中的"今天"统一固定为快照日期，避免模型看到日期不一致。

## 5. 指标

### 5.1 参考答案（人工标注）

覆盖率类指标需要"正确答案"。标注流程：

1. 从快照中导出每家公司的**候选事件池**：目标公司新闻（≤8 条）+ 每个邻居的新闻（≤5 条 × 邻居数），约 30–40 条。
2. 标注者（1 人）逐条判断：
   - `material`：这条新闻是否构成对**目标公司**有实质影响的事件（0/1）
   - `hop`：0 = 目标自身，1 = 1 跳邻居，2 = 2 跳
   - `polarity`：正面 / 负面 / 中性
3. 标注规范、边界案例与自检流程见 **`docs/annotation-guide.md`**。
4. 产出 `eval/gold/gold_events.csv`：

```csv
id,company,source_company,hop,relation,published_at,publisher,title,summary,url,material,impact_on_target,note
1,AAPL,TSM,1,供应商,2026-09-12,Bloomberg,TSMC warns...,...,https://...,1,negative,产能紧张影响苹果供应
```

`impact_on_target` **始终从目标公司视角**填写（竞争对手的利好 → 对目标是 negative）。

工作量估算：15 家 × 约 35 条 ≈ 500 条，只看标题和摘要，约 1.5–2 小时。
**注意**：不能用图谱自己抽取的事件当参考答案，否则等于自己给自己打分；标注必须在查看任何系统报告之前完成。

### 5.2 自动指标

| 编号 | 指标 | 定义 | 计算方式 |
|---|---|---|---|
| **M1** | 跨公司风险召回率（**主指标**） | 报告提到的 material 且 hop≥1 的事件数 / 该类事件总数 | 事件提及判定器（见 5.3） |
| M2 | 2 跳召回率 | 同上，限定 hop=2 | 同上 |
| M3 | 引用可核验率 | `key_signals` 与风险提示中，能在快照数据里找到依据的条数占比 | 判定器 + 人工抽查 |
| M4 | 编造率 | 报告中出现、但快照里不存在的公司 / 事件编号 / 关键数值的条数 | 公司名与事件编号可自动判定；数值由判定器 + 人工抽查 |
| M5 | 成本 | LLM 调用次数、输入/输出 token、端到端耗时 | 累加 API `usage` |
| M6 | 稳定性 | 3 次运行间：配置建议是否一致；提及的邻居事件集合的平均 Jaccard 相似度 | 纯代码 |
| M7 | 盲评胜率 | 成对盲评中被判为更好的比例 | 见 5.4 |

M1 是**唯一的主指标**，其余为次要指标，避免多重比较导致的"总能找到显著差异"。

### 5.3 事件提及判定器

对每份报告和该公司的候选事件池，调用一次评审模型：

```
给你一份投资研究报告，以及一组候选事件（编号 + 一句话描述 + 来源公司）。
判断报告中是否提到了每个事件（表述不同但指向同一事件算提到）。
输出 JSON：{"mentioned": [{"id": 3, "evidence": "报告中的原句"}], ...}
```

- 要求给出原句作为证据，便于人工复核。
- 三组统一用这一套判定，**不因为 C 组有事件编号就走另一条路径**，保证公平。
- **判定器校验**：人工复核约 50 条判定，计算一致率（Cohen's kappa）。kappa < 0.6 就需要修改提示词重来。

**评审模型的选择与风险**：评审同样使用 `claude-haiku-4-5`，与生成报告的是同一个模型。

- **对 M1/M2（事件提及判定）影响小**：这是客观任务——"报告里有没有提到这件事"，有原句作为证据，可人工核对，不涉及好坏偏好。
- **对 M7（盲评胜率）影响大**：模型可能偏好自己生成的文本风格（self-preference bias）。因此 **M7 只作为次要指标**，且人工抽查比例从 20% 提高到 **30%**；若人工与模型判定的一致率低于 0.7，M7 在报告中只作定性描述，不作为结论依据。
- 报告中必须写明"评审模型与生成模型相同"这一局限。

### 5.4 盲评协议

- 成对比较：同一公司、同一次重复的两份报告（A vs B、A vs C、B vs C）。
- 报告中**去掉能暴露分组的痕迹**：图谱章节、Mermaid 图、事件编号、"知识图谱"字样。
- 顺序随机化，评审模型不知道哪份来自哪组；允许判"平局"。
- 评分维度：风险识别是否全面、推理是否有依据、结论是否清晰可执行。
- 人工抽查 20% 的判定，确认与人工判断一致。

### 5.5 统计方法

- 以**公司为配对单位**（n=15），3 次重复取中位数后再做配对检验。
- 主指标 M1：**Wilcoxon 符号秩检验**（小样本、不假设正态），α = 0.05，报告中位数差与效应量 r。
- M7 胜率：二项检验（去掉平局）。
- 所有指标同时报告**均值 ± 标准差**和**中位数**，并在结论里明确 n=15 属于小样本。

## 6. 实现方案

### 6.1 目录结构

```
eval/
├── __init__.py
├── companies.txt          # 15 家公司清单
├── snapshot.py            # 录制 / 回放工具返回结果
├── variants.py            # A / B / C 的工具集合与 prompt
├── runner.py              # 批量执行，输出 runs/*.json
├── metrics.py             # M1–M6 计算
├── judge.py               # 事件提及判定、引用核验、盲评
├── report.py              # 汇总成 CSV + Markdown
├── gold/gold_events.csv   # 人工标注
├── snapshots/<日期>/<TICKER>.json
├── runs/<变体>/<TICKER>_<第几次>.json
└── results/               # 最终表格与报告
```

### 6.2 需要改动的生产代码（尽量小）

| 改动 | 原因 |
|---|---|
| `OrchestratorLoop.__init__` 增加可选参数 `tool_definitions` 与 `system_prompt` | 让实验注入 A/B/C 三种配置，默认值保持现状 |
| `messages.create` 增加 `temperature`（`config.TEMPERATURE = 0`） | 控制随机性 |
| Loop 记录每次调用的 `response.usage` 到 `self.usage_log` | 统计成本 |
| 工具层统一支持注入"数据来源"（market/news/sec/macro 都能接收 fetcher） | 快照回放；`news_fetcher` 已经支持 |

其余逻辑不动。所有改动都要补单元测试，保证默认行为不变。

### 6.3 数据格式

**快照**（`snapshots/2026-09-20/AAPL.json`）：
```json
{
  "recorded_at": "2026-09-20T09:00:00Z",
  "target": "AAPL",
  "neighbors": ["TSM", "AVGO", "QCOM", "GOOGL", "MSFT", "ASML"],
  "tools": {
    "query_market_data:AAPL:3mo": { "...工具原样返回..." },
    "query_news:TSM:5": { "..." }
  }
}
```

**单次运行**（`runs/C/AAPL_1.json`）：
```json
{
  "variant": "C", "company": "AAPL", "repeat": 1,
  "status": "ok",
  "draft": { "...emit_report 字段..." },
  "report_md": "...",
  "tool_log": [ "...（去掉 _graph 等大字段）..." ],
  "usage": {"calls": 11, "input_tokens": 52000, "output_tokens": 4200, "wall_seconds": 38.2}
}
```

**指标汇总**（`results/metrics.csv`）：
```csv
variant,company,repeat,m1_recall,m2_recall_hop2,m3_citation_ok,m4_hallucination,calls,input_tokens,output_tokens,wall_seconds,recommendation,confidence
```

### 6.4 命令行

```bash
python -m eval.snapshot  --companies eval/companies.txt --out eval/snapshots/2026-09-20
python -m eval.runner    --variant A --repeat 3 --snapshot eval/snapshots/2026-09-20
python -m eval.judge     --task mention      # 事件提及判定
python -m eval.judge     --task pairwise     # 盲评
python -m eval.report                        # 汇总 → results/
```

### 6.5 开销估算（量级）

| 项目 | 次数 |
|---|---|
| 报告生成 | A 约 4 次调用 / 份，B 约 6–10 次，C 约 11 次；135 份合计约 1,000 次 Haiku 调用 |
| 事件提及判定 | 135 次（每份报告 1 次，Haiku） |
| 盲评 | 3 组配对 × 15 公司 × 3 次 = 135 次（Haiku） |
| 外部数据请求 | 只在录制快照时发生，约 15 家 × (4 + 邻居数) ≈ 150 次 |

## 7. 风险与局限（结论中必须写明）

1. **样本小**：15 家公司、全部集中在美股科技与少量消费/汽车行业，结论不能外推。
2. **标注者只有 1 人**，无法计算标注者间一致性；只能用"同一标注者的自一致率（抽 30 条隔日重标，目标 ≥0.85）"和"判定器与人工的一致率"部分缓解。
3. **评审模型有偏好，且与生成模型相同**：可能偏爱更长、结构更完整的报告，也可能偏好自己的输出风格。用去标识化、顺序随机化、30% 人工抽查来缓解，但无法完全消除；M7 因此只作次要指标。
4. **种子关系是人工整理的**，B、C 两组共享同一份数据，所以实验衡量的是"如何使用关系"，**不是**"关系从哪来"。
5. **没有验证投资效果**：所有指标衡量的是报告质量，不是收益。
6. **快照固定在某一天**，无法反映不同市场环境下的表现。

## 8. 里程碑

| 阶段 | 内容 | 产出 |
|---|---|---|
| E1 | 生产代码的小改动（注入 prompt/工具集、temperature、usage 统计）+ 单测 | 默认行为不变 |
| E2 | 快照录制与回放 + A/B/C 三种变体配置 | `snapshots/`、`variants.py` |

E1–E3 大约 1 天，E4 的标注约 2 小时，E5 半天。
